# 0007. ソート・検索・ページ分割を API に任せ、取得に TanStack Query を使う

## 状態

採用

## 文脈

一覧のデータは `/api/facilitators` から取得します ([ADR 0003](0003-cors-proxy.md))。現行の API は、クエリの `page`・`limit`・`sort`・`order`・`search` で、ページ、1 ページの件数、ソートの列と向き、検索語を受け、条件に合う行 (`data`) と総件数 (`totalCount`) を返します (実測)。課題の PDF に載っている API 仕様の画像は古く、現行の API とはパラメータ名も応答の形も違います。

一覧は、ページ送り・ソート・検索のたびに条件が変わり、そのたびに取り直します。どこでソートや検索をするか、条件を切り替えたときの取得をどう扱うか、取り直しているあいだ画面に何を残すかを決めます。

## 決定

- ソート・検索・ページ分割は API に任せる。一覧の条件を API のクエリにして送り、1 ページの件数 (20) は `limit` として送る。検索語が無いときは `search` を送らない。
- 応答は zod のスキーマで検証する。行の型は機能の `lib` に置き、スキーマには `satisfies` を付け、検証した値がその型に合うことを型検査で確かめる。
- 取得関数が、検証した応答を 1 回だけ分類し (一覧 / 0 件 / 範囲外)、要求したページと一緒に結果に持たせる。表示と最終ページへの移動は、この分類を読むだけにする。範囲外の扱いは [ADR 0008](0008-list-state-in-url.md)、分類できない (矛盾した) 応答の扱いは [ADR 0009](0009-fetch-failure-handling.md) に書く。
- 取得は TanStack Query で行う。キーは一覧の条件そのものにし、条件が変わるとキーが変わって取得が走る。
- 一覧の取得の設定は、機能の `api` の `queryOptions` に書く。QueryClient は何も渡さずに作り、アプリ全体には TanStack Query の既定をそのまま当てる。本体とテストは同じ関数で QueryClient を作る。
- 一覧で既定から変えるのは次の項目にする。失敗に関わる設定 (再試行、オフラインのときの扱い) は [ADR 0009](0009-fetch-failure-handling.md) に書く。
  - `placeholderData: keepPreviousData`: 次の条件を取っているあいだ、前の一覧を残す。
  - `refetchOnWindowFocus: false`・`refetchOnReconnect: false`: タブに戻ったときと、ネットワークが再接続したときに取り直さない。`refetchOnReconnect` は `networkMode: 'always'` ([ADR 0009](0009-fetch-failure-handling.md)) のとき既定でも false だが、`networkMode` を変えても再接続で取り直さないよう明示する。
- キャッシュは既定のまま使う (使われなくなった結果は 5 分で捨てる。TanStack Query の doc の Important Defaults)。以前の条件に戻ったときは、残っている結果を先に出し、その上にローダーを重ねて取り直す。

## 根拠

- API がソート・検索・ページ分割と総件数を備えているので (実測)、画面は 1 ページ分 (最大 20 件) を受け取れば足ります。全件を取ってクライアントで並べる形は、いまの 30 件では成り立ちますが、件数が増えるほど 1 回に受け取る量が増え、成り立たなくなります。
- PDF の画像と現行の API の形が食い違っていたので、応答の形を信用せずに検証します。
- 行の型を `lib` に置くのは、`api`・`hooks`・`components` のすべてがこの型を使い、`lib` は機能の中のほかのディレクトリを import しないためです ([ADR 0005](0005-feature-directories-and-dependency-rules.md))。スキーマが `lib` の型にある項目を欠くと `satisfies` で型検査が落ちるので、型と検証のずれに型検査で気づけます。
- 分類を取得関数で 1 回だけ行うと、表示と最終ページへの移動が同じ分類を読むので、判定が食い違いません。結果に要求したページを持たせるのは、前の一覧を残しているあいだも、件数表示 (「N件中 a〜b件」) を出している行に合わせるためです。
- TanStack Query は、条件をキーにした取得、条件を切り替えたときの前の取得の中断、前の結果の引き継ぎ、キャッシュを受け持ちます。これらを自前で書かずに済みます。
- `keepPreviousData` は、キーを問わず、最後にデータを持っていたクエリの結果を出します (TanStack Query の doc の Paginated Queries、query-core のソース)。ページ送りやソートのたびに一覧が消えず、前の一覧の上にローダーを重ねられます。
- 一覧の取得の設定を機能の `queryOptions` に書くのは、一覧の要件 (前の一覧を残す、取り直さない場面、失敗の扱い) を機能のファイルで読めるようにし、アプリ全体の既定を一覧の都合で変えないためです。本体とテストが同じ関数で QueryClient を作るので、テストも本体と同じ設定で動きます。

## 採らなかった案

- **全件を取ってクライアントで処理する**: いまの件数では成り立ちますが、件数が増えると成り立ちません。API が同じ処理を備えているので、画面の側で持つ理由がありません。
- **Effect の中で `fetch` する**: 競合状態 (先に送った要求の応答が後から届く) とキャッシュを、自分で扱うことになります (react.dev の案内)。
- **応答を型の宣言だけで信用する**: 応答の形が型と違っても実行時には検査されないので、PDF の画像と現行の API のような食い違いに気づけません。
- **検証を手で書く**: 型と検証を別々に書くので、応答の形が変わったときに、型と検証がずれます。
