# 0009. 取得の失敗の範囲と扱い

## 状態

採用

## 文脈

課題は、通信エラーのときにダイアログを出し、リトライできることを求めています。API は速く、失敗もしないので (実測)、失敗の扱いは応答を差し替えたテストで確かめます。

取得が失敗する形は、通信そのものの失敗と、届いた応答が使えない場合に分かれます。どこまでを失敗とし、失敗したときに何を出し、どう取り直すかを決めます。TanStack Query の既定には、再試行とオフラインのときの扱いで、この一覧の要件と合わないものがあります。

## 決定

- 次の 6 つを取得の失敗にする。
  - 通信の失敗 (`src/lib/http.ts` の `HttpError`。原因を `kind` に持つ): ネットワーク断 (`network`)、10 秒のタイムアウト (`timeout`)、HTTP の状態が成功を示さない (`status`。`response.ok` が偽)、本文を JSON として読めない (`parse`)。
  - 応答の不正 (機能の `api` の `InvalidResponseError`。理由を `reason` に持つ): 応答がスキーマに合わない (`schema`)、行が空なのに総件数が 1 以上で、要求したページは範囲内 (`inconsistent`)。
- 呼び出し元 (TanStack Query) が取得を中断したときは、失敗にしない。通信の失敗の型にせず、元のエラー (`AbortError`) のまま投げ直す。
- タイムアウトは `AbortSignal.timeout` で作り、呼び出し元の `signal` と `AbortSignal.any` で合わせて `fetch` に渡す。どちらが先に起きても `fetch` を止め、呼び出し元の `signal` が中断されているかで、中断とタイムアウトを見分ける (本文を読んでいる途中も同じ)。
- 画面は、6 つのどれも同じ通信エラーとして扱い、同じダイアログを出す。ダイアログが受け取るのは開閉の真偽値とリトライの関数だけで、失敗の種別を読むのはテストだけにする。
- ダイアログのボタンは「リトライ」だけにし、Esc と外側のクリックでは閉じない。
- 「リトライ」は同じ条件を取り直す。ダイアログを出すのは「失敗していて、取り直し中でない」ときにし、取り直しているあいだは閉じてローダーを出し、また失敗したら開き直す。
- 自動の再試行はしない (`retry: false`)。やり直しは利用者の「リトライ」に任せる。
- オフラインでも取得し、失敗としてダイアログを出す (`networkMode: 'always'`)。
- 失敗しているあいだ、ダイアログの後ろには取得できている結果だけを出す。出せる結果が無いとき (初回の失敗や、条件を変えた先での失敗) は、ヘッダー・見出し・検索欄だけの画面になる。条件を変えた先で失敗してリトライすると、背後の一覧が「出る → 消える → 出る」と往復する。これは仕様とし、ユニットテストで固定する。

## 根拠

- 6 つのどれが起きても、表示に使える応答がありません。矛盾した応答は、表示できる行が無いのに総件数があるので、0 件とも言えません。そのため 0 件の文言ではなく、失敗として扱います。
- 通信の失敗と応答の不正で型を分けるのは、共有の層が先生や API の形を知らないためです ([ADR 0005](0005-feature-directories-and-dependency-rules.md))。`src/lib/http.ts` は通信だけを知り、応答の形に関わる失敗は機能の `api` が定義します。
- 画面にとっては、どの失敗も「一覧を取れなかった」ことに変わりはなく、利用者が取れる手も「リトライ」で同じです。ダイアログに種別を渡さないので、ダイアログは機能の事情を知らずに済みます。
- 呼び出し元の中断は、呼び出し元が自分で止めたもので、通信の失敗ではありません。TanStack Query は、`AbortSignal` を使った取得が中断されると、クエリを前の状態に戻します (TanStack Query の doc の Query Cancellation)。中断を失敗の型に変えずに投げ直し、扱いを TanStack Query に任せます。
- タイムアウトも中断と同じ仕組み (`AbortSignal`) で `fetch` を止めるので、どちらで止まったかを呼び出し元の `signal` で見分けます。Vitest の jsdom でも `AbortSignal.any` と `AbortSignal.timeout` が使えるので、タイムアウトと中断の区別をユニットテストで確かめています。
- TanStack Query の既定は、失敗したら 3 回まで再試行します (TanStack Query の doc の Important Defaults)。既定のままでは、再試行を終えるまでダイアログが出ず、失敗を知らせるのが遅れます。失敗はすぐ知らせ、やり直すかは利用者が決めます。
- `networkMode` の既定の `online` は、オフラインを検知すると、取得を失敗させずに止めます。`always` にすると、接続状態を無視して取得し、失敗すればエラーの状態になります (TanStack Query の doc の Network Mode)。既定のままでは、オフラインのとき、ローダーもダイアログも出ません。
- データのあるクエリを取り直すあいだ、`status` は `error` のままで、データの無いクエリは `pending` に戻ります (query-core の `fetchState`)。失敗の状態だけでダイアログの開閉を決めると、データのある条件のリトライでは、取り直しのあいだもダイアログが開いたままになります。そのため、取り直し中かどうかも見ます。
- 背後の一覧の往復は、前の一覧の引き継ぎ (`keepPreviousData`) が、データが無く `status` が `pending` のあいだだけ使われ、失敗の状態では使われないために起きます (TanStack Query の doc の Paginated Queries、query-core のソース)。条件を変えた先で失敗すると `error` になって引き継ぎが外れ、一覧が消えます。リトライを始めると、データの無いクエリは `pending` に戻るので、引き継ぎが使われて一覧が出ます。

## 採らなかった案

- **TanStack Query の既定の再試行 (3 回まで) を使う**: 再試行を終えるまでダイアログが出ず、失敗を知らせるのが遅れます。
- **`networkMode` を既定の `online` のままにする**: オフラインのとき、ローダーもダイアログも出ません。
- **矛盾した応答を 0 件として出す**: 総件数があるのに、0 件の文言を出すことになります。
- **通信の失敗と応答の不正を 1 つの型にする**: 共有の層が応答の形を知ることになり、依存の向き ([ADR 0005](0005-feature-directories-and-dependency-rules.md)) に反します。
